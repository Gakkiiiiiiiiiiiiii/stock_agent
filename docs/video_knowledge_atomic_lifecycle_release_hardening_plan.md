## 2. P1：生产 PostgreSQL 迁移适配加固

涉及文件：

- `storage/bootstrap.py`
- `storage/migrations/007_video_knowledge_v3_schema.sql`
- `storage/migrations/008_knowledge_lifecycle_audit.sql`
- `storage/migrations/009_knowledge_extraction_quality_metrics.sql`
- 可新增：
  - `storage/migrations/postgres/007_video_knowledge_v3_schema.sql`
  - `storage/migrations/postgres/008_knowledge_lifecycle_audit.sql`
  - `storage/migrations/postgres/009_knowledge_extraction_quality_metrics.sql`
  - `tests/test_migrations.py`

当前观察：

`storage/bootstrap.py` 中存在如下逻辑：

```python
if not is_sqlite and "AUTOINCREMENT" in sql.upper():
    conn.execute(text("INSERT INTO schema_migration(version) VALUES (:version)"), {"version": path.name})
    continue
```

这意味着包含 `AUTOINCREMENT` 的迁移在非 SQLite 数据库上会被直接标记为已应用，但 SQL 本身不会执行。

对当前本地测试影响：

- 本地测试主要使用 SQLite。
- `Base.metadata.create_all()` 会在测试库中创建 ORM 模型对应的表。
- 因此本地全量测试可以通过。

生产风险：

- PostgreSQL 环境下，`007 / 008` 迁移可能不会执行原始 SQL。
- 如果生产环境依赖迁移脚本而不是 ORM `create_all()`，新表、索引或后续变更可能缺失。
- `schema_migration` 已记录成功，会掩盖实际未执行的问题。
- 复合索引、手写索引、未来 ALTER 类迁移无法完全依赖 ORM 自动创建。

修改要求：

1. 不要在非 SQLite 环境中简单跳过含 `AUTOINCREMENT` 的迁移。
2. 为 SQLite 和 PostgreSQL 拆分迁移目录或迁移文件。
3. PostgreSQL 版本使用：
   - `BIGSERIAL PRIMARY KEY` 或 `GENERATED BY DEFAULT AS IDENTITY`
   - `BOOLEAN DEFAULT FALSE`
   - PostgreSQL 兼容的 `TIMESTAMP` / `TEXT` / `VARCHAR`
4. `schema_migration` 只能在迁移实际执行成功后写入。
5. 对重复列、重复索引、重复表做显式幂等处理。

建议方案：

```text
storage/migrations/
  sqlite/
    007_video_knowledge_v3_schema.sql
    008_knowledge_lifecycle_audit.sql
    009_knowledge_extraction_quality_metrics.sql
  postgres/
    007_video_knowledge_v3_schema.sql
    008_knowledge_lifecycle_audit.sql
    009_knowledge_extraction_quality_metrics.sql
```

`apply_sql_migrations()` 根据 `engine.url.get_backend_name()` 选择目录。

如果暂时不拆目录，可先做最小修复：

- 保留当前 SQLite SQL。
- 增加 PostgreSQL 专用转换或专用迁移文件。
- 移除“跳过并标记成功”的逻辑。

建议测试：

- `test_sqlite_migrations_apply_once`
- `test_sqlite_migrations_are_idempotent`
- `test_postgres_migration_does_not_mark_skipped_autoincrement_as_applied`
- `test_knowledge_extraction_run_metrics_column_exists_after_migration`

验收标准：

- SQLite 本地测试仍通过。
- PostgreSQL 不会把未执行的迁移标记为成功。
- 新知识表、生命周期审计表、metrics 字段在生产库可验证存在。

## 3. P1：真实视频端到端冒烟验收

涉及文件：

- `engines/content/video_ingest_service.py`
- `workers/job_worker.py`
- `workers/vector_index_worker.py`
- `app/api.py`
- `mcp_servers/content_server.py`
- 可新增：
  - `scripts/smoke_video_knowledge_pipeline.py`
  - `tests/test_video_knowledge_smoke_contract.py`

当前状态：

单元测试和接口测试已覆盖主要逻辑，但还缺一个接近真实流程的冒烟验收脚本。

修改目标：

提供一个可重复执行的真实或仿真视频知识全流程检查：

```text
提交视频解析任务
→ 生成 transcript / frame insights
→ 构建 chapter
→ 抽取 KnowledgeUnit
→ schema 校验
→ temporal policy
→ dedup/conflict
→ 入库
→ 向量任务入队
→ worker upsert
→ search_video_knowledge 检索
→ current/history 查询
→ lifecycle update
→ vector delete 任务
→ audit 查询
```

脚本建议输出：

- `video_id`
- `task_id`
- `chapter_count`
- `knowledge_unit_count`
- `evidence_coverage`
- `ocr_evidence_unit_count`
- `low_evidence_unit_count`
- `vector_task_count`
- `search_hit_count`
- `lifecycle_audit_count`
- `warnings`

验收标准：

- 至少一个样例视频或仿真输入可完整跑通。
- 每条正式知识至少有一条 evidence。
- 搜索能召回刚入库的知识。
- 人工下线后创建 delete 向量任务。
- 冒烟脚本失败时返回非零退出码。
